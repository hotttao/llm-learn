# 01 · 本体理论：从第一性原理出发

> 本文的目标不是让你「记住本体的定义」，而是让你**自己推导出它**——以至于即使忘掉所有名词，
> 你也能在任何 Agent 系统设计评审中，指出「这里缺一层什么」。

---

## 1. 六步推导：为什么 Agent 一定需要本体

### 第 1 步：Agent 的本质是「改变世界状态的循环」

一个 Agent 无论多复杂，都可以还原为：

```
感知(Perceive) → 决策(Decide) → 行动(Act) → 世界状态改变 → 再感知 ……
```

它与「聊天机器人」的本质区别就在最后两步：**聊天只产生文本，行动改变世界**——发出订单、
重启服务、写数据库、给客户退款。

### 第 2 步：决策依赖世界模型，而世界模型依赖「存在约定」

要做出正确决策，Agent 必须能回答三类问题：

| 问题 | 依赖 | 例子 |
|---|---|---|
| 现在世界上**有什么**？ | 状态词汇（名词） | 「有哪些服务？它们的依赖关系是什么？」 |
| 我**能做**什么？ | 能力词汇（动词） | 「我可以重启它吗？重启需要什么前提？」 |
| 做了**会发生什么**？ | 转移规则（副词/约束） | 「重启后告警会消失吗？会不会违反 SLO？」 |

这三样东西合起来，就是一个**世界模型的词汇表和语法**。

### 第 3 步：LLM 是「语义引擎」，但不是「存在引擎」

LLM 的知识有三个致命结构特性（这是第一性原理层面的限制，不是 prompt 能修的）：

1. **隐式的**：知识藏在 175B/671B 个参数里，没有一处可以指着说「Order 的定义在这里」；
2. **概率的**：同一个上下文里问两次「退款单包含哪些字段」，可能得到两个不同答案；
3. **无状态的**：每次推理之间不维护任何「世界当前是什么样」的账本。

一个只会「大概理解意思」但**不维护存在账本**的系统，不能独立承担「改变世界」的责任。
这就是 2023–2024 年大量 Agent demo 炫酷、生产翻车的结构性原因。

### 第 4 步：行动的下游要求「一致性」，而一致性要求「共享规范」

当 Agent 调用工具 `restart_service("payment-db")` 时，这句话要成立，必须有以下共识：

- 工具的提供方（监控系统）和调用方（Agent）对 `Service` 的身份标识达成一致（是名字？ID？ARN？）；
- 「重启」的**前置条件**（必须先有故障单？）和**效果**（状态变健康？告警清除？）双方理解一致；
- 如果还有第二个 Agent、一个人类值班员在协作，他们也得用**同一套**理解。

没有共享规范，每一次工具对接都是一次隐式约定的口头协议——规模一大必然崩坏。
这就是 IETF 多 Agent 协作协议草案（MACP, 2026）明确指出的现状：
**A2A 解决了消息怎么传，但没有标准化「消息里的词是什么意思」——语义互操作层是缺失的**，
而这正是本体补位的地方。

### 第 5 步：把「约定」显式化、形式化、可共享化

软件工程史上有两次同类事件：

- 数据库时代：数据结构的约定从「应用程序里的口头约定」显式化为 **Schema**（DDL）；
- 微服务时代：接口的约定从「文档 wiki」显式化为 **API Contract**（OpenAPI/protobuf）；
- **Agent 时代（现在）：世界模型的约定正在从「prompt 里的自然语言描述」显式化为 Ontology。**

一句话版本：

> **Ontology 之于 Agent，如同 Schema 之于数据库、API Contract 之于微服务。**

### 第 6 步：结论

> **本体 = 一个系统中「存在什么、如何关联、能做什么、按什么规则做」的显式、形式化、可共享的规范说明。**

它同时服务四方（这是它区别于普通文档的关键——**一份定义，四处执行**）：

| 使用者 | 怎么用 |
|---|---|
| LLM | 作为提示词的一部分被「阅读」，约束它的输出空间 |
| 验证器 | 作为机器可执行的规则，校验状态与动作的合法性 |
| 执行器 | 作为分派依据，路由动作、应用效果 |
| 人类 | 作为可评审、可版本化的治理资产 |

## 2. 本体是什么、不是什么

### 2.1 经典定义

> "An ontology is an **explicit specification of a conceptualization**."
> —— Tom Gruber (1993)，斯坦福
> 「本体是对某个概念化的显式规范说明。」

拆开看：
- **概念化（conceptualization）**：你脑中对这个世界那部分的模型——有哪些对象、关系、规则；
- **显式规范（explicit specification）**：把它用某种可交流的形式**写下来**，且写得足够精确。

你写一个 README 描述业务概念，算「半显式」；写成带类型、约束、机器可校验的形式，才是工程意义上的本体。

### 2.2 和近邻概念的区别（面试高频）

| 概念 | 回答的问题 | 例子 | 与本体的关系 |
|---|---|---|---|
| 受控词表 | 允许用哪些词？ | 国家代码表 | 本体的最底层基座 |
| 分类法 | 词之间是什么层级？ | 生物分类树 | 单一层级关系（is-a） |
| Schema | 数据长什么样？ | 数据库 DDL、JSON Schema | 只管结构，通常不管语义公理 |
| 知识图谱 | 具体有哪些实例和事实？ | «payment-api» 依赖 «payment-db» | **实例层（ABox）**；本体是它的 **模式层（TBox）** |
| 本体 | 概念的本质、关系与**公理**是什么？ | 「重启 是一种 变更动作，前置条件是存在未解决故障」 | 模式 + 语义约束 + 共享词汇 |

**最重要的二分：TBox / ABox**（来自描述逻辑）：
- **TBox**（Terminology Box，术语盒）= 本体 = 概念与规则的集合——「什么是 Incident」；
- **ABox**（Assertion Box，断言盒）= 知识图谱 = 具体事实的集合——「INC-1001 是一个 Incident」。

工程口诀：**图谱可以脏，本体必须净。** 实例数据允许出错、允许冲突，事后清洗；
但模式层的歧义会污染所有下游实例。

### 2.3 表达力谱系（不要一上来就上最高档）

```
受控词表 → 分类法(taxonomy) → 纲要(schema) → 本体(ontology) → 形式本体(带推理公理)
   低成本、低表达 ————————————————————————————————→ 高成本、高表达
```

OWL-DL 能表达「 uncle = brother ∃ parent」这种可推理的公理，但你付的是**工程复杂度**。
Agent 工程的主流甜点区在**中间档：结构化 schema + 声明式约束（SHACL 风格）+ 自然语言标注**，
这正是我们实战项目采用的形态。

## 3. 简史：三次浪潮与两次冬天（为什么这次不一样）

了解这段历史的人，才能判断「这次是不是又一次炒作」。

### 第一次浪潮：符号主义时代（1970s–1980s）

- 哲学源头：亚里士多德《范畴篇》研究「存在物的分类」——ontology 一词即「关于存在（onto）的学问（-logy）」；
- Minsky 的框架（Frame）理论、KL-ONE 知识表示语言；
- 顶点：CYC 工程——试图人工录入人类全部常识知识。

**冬天原因：知识获取瓶颈（knowledge acquisition bottleneck）。**
让领域专家和知识工程师一条条人工录入规则，成本指数级增长，收录永远赶不上世界变化。

### 第二次浪潮：语义网时代（1990s–2000s）

- Berners-Lee 提出语义网（Semantic Web）愿景；W3C 标准化 RDF / RDFS / OWL / SPARQL；
- Grubar/Studer 完善本体定义；Stanford 提出「七步法」本体工程方法论；
- Agent 侧：FIPA ACL 试图为多 Agent 系统标准化「言语行为」（这条脉络 2025 年在 A2A 里复活了）。

**冬天原因：工程成本高、收益闭环弱。**
写一个 OWL 本体需要专家 + 逻辑学训练，而下游应用（语义检索）带来的收益撑不起成本。
互联网公司转向了更务实的**轻量知识图谱**（Google Knowledge Graph, 2012）和 schema.org。

### 第三次浪潮：Agent 时代（2024– ）

**为什么这次不一样？关键在于知识获取成本发生了数量级反转：**

| | 前两次 | 现在 |
|---|---|---|
| 从文档抽取结构化知识 | 人工，每条小时级 | LLM，每条秒级、边际成本≈token 费 |
| 生成本体草稿 | 专家从零写 | LLM 生成候选 + 人审核（ OntoCast 等已产品化此流程）|
| 使用本体 | 需要推理机专家 | **LLM 本身就是最好的「本体阅读器」** |

前两次浪潮死因是「录入太贵、消费太难」，而 LLM 恰好把两端都解决了。
这就是为什么 2025 年起学术界出现大量 "agentic ontology" 方向（用 agent 构建本体、
用本体约束 agent），企业侧 Palantir 把 Ontology 作为其 AIP 平台的核心抽象售卖多年后，
整个行业开始跟进。

## 4. Agent 本体栈：五层模型（本课程的核心框架）

把本体当成一个分层栈来理解，每层解决 Agent 的一个独立问题：

```
┌─────────────────────────────────────────────────────────┐
│ L4 角色与目标本体  谁负责什么？目标如何分解？            │  BDI（信念-愿望-意图）、
│                   Agent 的社会结构                       │  角色权限、目标层级
├─────────────────────────────────────────────────────────┤
│ L3 交互本体        多方如何协作对话？                     │  消息类型、回合结构、
│                   协作的语法                             │  A2A/ACP、FIPA ACL 传统
├─────────────────────────────────────────────────────────┤
│ L2 能力本体        能做什么？做了会怎样？  ★价值最快      │  动作 + 前置条件 + 效果
│                   世界的转移函数                           │  + 风险等级（MCP 工具是雏形）
├─────────────────────────────────────────────────────────┤
│ L1 领域本体        世界里有什么？如何关联？                │  实体 + 关系 + 约束
│                   状态的名词词汇                           │  （TBox，SHACL 约束）
├─────────────────────────────────────────────────────────┤
│ L0 表示层          用什么形式写下来？                      │  OWL/RDF、LinkML、
│                   机器可读 + 人类可读的载体               │  JSON-LD、（轻量）YAML
└─────────────────────────────────────────────────────────┘
```

**逐层要点：**

- **L1 领域本体（名词层）**：定义实体类型、属性、关系和**状态约束**。例：「critical 服务
  副本数不得低于 2」。它决定 Agent「看世界」的分辨率。
- **L2 能力本体（动词层）**：每个动作声明**参数 schema、前置条件、效果、风险等级**。
  例：「restart_service 前置条件=存在 open 状态的 Incident，效果=status→healthy」。
  这是给 Agent 装「因果模型」的一层，也是护栏所在。**实践上建议从这层入手**——它比
  领域本体更小、见效更快（见 02 最佳实践第 2 条）。
- **L3 交互本体（协议层）**：多 Agent / 人机之间的消息类型与回合结构。A2A 定义了
  task/artifact 的语法，但 IETF MACP 草案指出它**不定义语义**——两个 Agent 对
  「报告完成」的理解是否一致，仍然要靠共享本体。
- **L4 角色与目标本体（社会层）**：经典 BDI 架构（Belief–Desire–Intention）的现代回声。
  谁有权做什么（对接 RBAC）、目标如何分解委派（planner 的输入）。
- **L0 表示层**：不要教条。OWL 表达力最强但工程重；**LinkML / JSON Schema + 自然语言
  标注 + 声明式约束**是 Agent 工程的务实甜点；我们的项目用带 schema 语义的 YAML 从零实现，
  目的是让你看穿所有表示层的共同骨架。

## 5. 与当代 Agent 范式的精确映射

你已经在用的一些东西，其实就是本体的局部形态——这张表帮你在旧知识和新框架之间建立索引：

| 你熟悉的 | 它在本体栈中的位置 | 它缺什么 |
|---|---|---|
| Function Calling 的参数 JSON Schema | L2 能力本体的参数部分 | 缺前置条件、效果、风险——工具间组合语义 |
| MCP（Model Context Protocol） | L0–L2 的**传输标准**：能力本体怎么被服务器暴露给客户端 | 语义仍未标准化：同一个语义，不同 server 命名/粒度各异 |
| A2A / ACP 协议 | L3 交互本体 | 不定义词汇语义（IETF MACP 明确指出的缺口） |
| GraphRAG | L1 本体（schema）+ ABox（图谱实例） | 常缺约束与动作，只服务检索 |
| 语义层 / Semantic Layer（指标层） | L1 领域本体的分析视图 | 通常只覆盖「指标」不覆盖「动作」 |
| BDI / Planner 架构 | L4 + L2 的结合 | 经典实现重，现代趋势是用 LLM 当 planner、本体当世界模型 |
| Palantir Ontology | 全栈版本：Object/Link/Action 三件套 | 闭源工业实现，正是本文框架的参照物之一 |
| Prompt 里写「你有这些工具…」 | 无本体——隐式、不可验证的口头约定 | 一切（这就是被取代的对象） |

**核心判断标准**：一个约定是不是本体，看它是否**显式（写下来了）、形式化（机器可校验）、
可共享（多方共同使用）**。Prompt 里的工具描述只满足第一条，所以它只是本体的退化形态。

## 6. 2025–2026 前沿：双向关系

当前研究和工业实践可以总结为一条**双向飞轮**：

```
        ┌────────── 本体约束 Agent（信任方向）──────────┐
        │   · KG 作为 LLM Agent 的信任来源（Sequeda 等, 2025）
        │   · 本体约束 + 形式验证拦截 agent 的越界行为
        │   · 神经符号架构：LLM 提语义，本体提供接地（arXiv:2604.00555）
        ▼
   【 本体 ⇄ Agent 】
        ▲
        │   · Agentic Ontology of Work（Skan AI, 2026）：8 种实体
        │     建模「工作」本身的通用本体
        │   · OntoCast：LLM agent 从文档构建 RDF 知识图谱
        │   · FlyBench（arXiv:2603.21846）：agentic 本体策展基准
        └────────── Agent 构建本体（生产方向）──────────┘
```

- **信任方向（本体 → Agent）**：用本体的形式约束验证 agent 产生的查询与动作，
  拦截幻觉。这是「神经（会联想）+ 符号（有边界）」的神经符号回归。
- **生产方向（Agent → 本体）**：LLM 把「从非结构化文档抽取结构化本体/图谱」的成本
  打到边际趋零，本体工程从「专家手工艺」变成「生成 + 人审的流水线」。
- **工业标志事件**：IETF MACP 草案（2026-05）把「多 agent 协作缺本体层」写进了
  标准化议程；企业架构咨询把 MCP+A2A+治理框架并列为企业 Agent 的三件套。

一句话总结前沿：**本体不再是知识工程的奢侈品，而是 Agent 互操作与治理的必需品；
同时 LLM 让本体本身的制造成本崩塌——供需两端同时到位。**

## 7. 常见误解 FAQ

**Q1：本体 = 知识图谱？**
不是。本体是模式层（TBox），图谱是实例层（ABox）。图谱回答「具体事实」，本体回答「概念与规则」。二者配合使用。

**Q2：我用了 Function Calling，就已经有本体了吗？**
你有了能力本体的参数 schema 零件。但缺前置条件、效果、风险等级，以及领域层和交互层。好比有了一张桌子腿，不等于有桌子。

**Q3：本体是不是要一开始设计完备才能开工？**
恰恰相反。现代实践是「最小可行本体（MVO）」+ 演化，与敏捷完全兼容（见 02 最佳实践第 3 条）。

**Q4：本体和 RAG 什么关系？**
RAG 解决「把相关知识塞进上下文」，本体解决「塞进来的东西在结构上和语义上是否一致」。GraphRAG 可以理解为「本体作为检索的骨架」。

**Q5：为什么不用大 prompt 直接把规则写给 LLM？**
Prompt 是消费方，不是资产的单一事实源：验证器读不了 prompt、执行器无法从中分派、无法做迁移和 diff。本体是**一份定义、四处执行**（LLM 读、验证器验、执行器派、人类审），prompt 只是其中一处投影。
