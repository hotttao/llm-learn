# 04 · 对话窗口与部署架构：表现形态、一层 Tool 模式与 A2A 演进

> 本篇回答两个高频问题：
> 1. 这个 Agent 对人的**表现形态**是什么？一个聊天框就够了吗？
> 2. 对话窗口**怎么实现**——把运维 Agent 作为 tool 挂进对话 Agent（一层），
>    还是走 A2A 做多 Agent 对等调用（多层）？
>
> 结论先行：**界面是「对话 + 面板」的混合形态；架构默认选一层（Tool/MCP 模式）**，
> 理由与升级时机见下。

---

## 1. 表现形态：一个窗口装不下，需要四个界面

| 界面形态 | 承载什么 | 对应本体层 | 为什么不能用对话替代 |
|---|---|---|---|
| **对话窗口** | 人的*意图*输入、Agent 的*推理叙述* | L4 目标层 | 模糊目标的协商只有自然语言高效 |
| **世界状态页面**（拓扑图/表格/看板） | 当前世界*是什么样* | L1 领域本体 | 人扫表格比读对话快十倍 |
| **动作卡片 + 审批按钮** | Agent *提议做什么*（参数、前置条件检查结果、批准/拒绝） | L2 能力本体 + 策略层 | 高风险操作的治理必须给显式 affordance |
| **审计时间线** | *已经发生了什么*：每步动作、被拦记录、依据规则 | ActionRecord 台账 | 事后追责与复盘的结构化账本 |

**核心原则：UI 也是本体的一种投影。** 本课程的贯穿主线是「一份定义，四处执行」
（LLM 读、验证器验、执行器派、人审阅）——前端只是第五个消费者：

```
本体(YAML) ──投影──→ ① 提示词（给 LLM）        describe_for_llm()
                ├──→ ② 校验规则（给验证器）      validate_world()
                ├──→ ③ 分派依据（给执行器）      execute()
                ├──→ ④ 文档（给人审阅）          inspect
                └──→ ⑤ 界面（给人操作）          拓扑图/表单卡片/时间线
```

因为实体有类型（`Dependency` 关系）→ 自动渲染拓扑图；`Incident.status` 是枚举 →
自动渲染看板列；动作有参数 schema → 自动生成审批卡片的表单。这是 Palantir AIP
（左对话 + 右侧 Ontology 对象组件）的产品形态验证过的路径。

**一个容易被忽略的对称性**：人点「批准」按钮本身也是能力本体里的一个动作——
走同一个执行器、写同一条审计轨迹。事后审计时，
`restart_service 由 agent 发起 + human 批准` 与 `rollback 由 human 直接发起`
是同构的两条记录，责任链完整。

## 2. 选型：Tool 模式（一层） vs A2A 模式（多层对等）

### 2.1 对比

| | **Tool 模式（一层）** ★推荐起步 | A2A 模式（多层对等） |
|---|---|---|
| 架构形态 | 对话 agent 是大脑，运维 agent 是手脚：**垂直组合** | 两个对等 agent，各有循环与目标：**水平联邦** |
| 标准载体 | MCP（tool schema = 能力本体的投影） | A2A（agent card + task/artifact） |
| 世界状态 | 一份，收在运维侧执行器 | 各有各的，靠消息对齐（语义互操作难题） |
| 对话权 | 用户只跟对话 agent 说话 | 每个 agent 都可直接与人交互 |
| 延迟/复杂度 | 一次函数调用 | 一轮协议协商 |
| 治理 | 审批/审计/账本不动，原地保留 | 需要跨 agent 账本对齐方案 |

### 2.2 决定性的三个硬问题

1. **被调用方有没有独立的目标和生命周期？**
   OntoOps 没有——它不自己决定「今晚排查什么」，只接受目标、在护栏内执行、交回结果。
   它的智能是「本体护栏 + 执行器」，不是自主性。**没有独立目标的东西就是 tool，
   无论内部多复杂。**
2. **治理边界在哪？** 审批、审计、状态账本收在运维侧的 ①–⑧ 生命周期里。
   Tool 模式下原样不动；A2A 下要重新解决两个账本如何对齐。
3. **康威定律**：同一团队维护 → tool；运维能力由独立团队运营、服务多个异构消费方 → A2A。

### 2.3 一个反直觉要点

包成 tool 的**不是运维 Agent 的 LLM 循环，而是它的执行器**。
对话窗口的 LLM 负责意图理解与叙述（智能在外壳），OntoOps 负责护栏执行（治理在内核）。
所以「一层」并不矮化运维 Agent——它是**带本体治理的服务化执行引擎**，
换任何对话外壳都不用改内核。

## 3. 架构图

### 3.1 当前项目内核（教学形态，CLI 直驱）

```
┌───────────────────────────────────────────────────────────────┐
│ cli.py  demo / chat / inspect / validate                        │
└──────────────┬────────────────────────────────────────────────┘
               │ 每轮：prompt = 本体投影 + 世界投影 + 历史
               ▼
┌───────────────────────────────────────────────────────────────┐
│ agent.py  Agent 循环（感知 → 规划 → 行动）                       │
│   LLM 决策 {action, params}；被拦动作结构化回喂，允许自我修正      │
└──────────────┬────────────────────────────────────────────────┘
               │ executor.execute(action, params)
               ▼
┌───────────────────────────────────────────────────────────────┐
│ actions.py  执行器：一次动作调用的完整生命周期                     │
│   ①dispatch ②param(schema+实体解析) ③precondition(语义合法性)    │
│   ④policy(治理审批) ⑤handler(外部副作用) ⑥effects(声明式效果)    │

│ 实体账本 + 快照/回滚    │◄─────│ 约束四要素: scope/where/ │
└───────────┬───────────┘ 查询 │ require/message        │
            │                  └────────────────────────┘
```

### 3.3 审批流时序（Tool 模式下不阻塞 server）

```
对话LLM          MCP Server(执行器)            人
   │ ops_execute(restart, db)  │                 │
   │──────────────────────────►│                 │
   │                           │ ④命中策略: 需审批 │
   │   返回 {status: pending_approval,            │
   │         ticket: APR-001, rule: high-risk}    │
   │◄──────────────────────────│                 │
   │ 渲染动作卡片(参数+前置条件)                    │
   │─────────────────────────────────────────────►│
   │                                             │ [点击 批准]
   │ ops_execute(approve, {ticket: APR-001})      │
   │──────────────────────────►│ ⑤⑥⑦⑧ 继续生命周期 │
   │   返回执行结果 + 审计记录                       │
   │◄──────────────────────────│                 │
```

要点：审批**不在 server 里阻塞等人**，而是返回 `pending_approval` 票据；
「approve」本身是能力本体里的一个动作，与 agent 发起的动作同构入账（第 1 节的对称性）。

### 3.4 演进形态：多层 A2A（出现明确信号时才升级）

```
┌──────────────────┐   A2A task    ┌──────────────────────┐
│  排障 Agent       │◄─────────────►│  审批 Agent           │
│ (OntoOps 内核+LLM)│  artifact/结果 │ (独立责任域，可寻人)   │
└───────┬──────────┘               └──────────────────────┘
        │ A2A                       ┌──────────────────────┐
        ├──────────────────────────►│  复盘 Agent           │
        │                           └──────────────────────┘
        ▼                    各 Agent 之间唯一的公共词汇
┌────────────────────────────────────────────┐
│      共享本体（core + capabilities + 协议词汇）│ ← 语义互操作层
└────────────────────────────────────────────┘
```

升级触发器（满足其一）：
1. 多个责任域需要**互相协商**（排障 Agent 要主动找审批 Agent，而非被调用）；
2. 运维能力要**服务多个异构消费方**（不同团队的不同对话外壳）；
3. **组织分家**：运维能力由独立团队运营（康威定律）。

届时只把 MCP 外壳换成 A2A server，本体与执行器原样保留。

## 4. MCP tool 面设计（一层模式的接口契约）

| Tool | 来源（本体投影） | 返回 |
|---|---|---|
| `ops_list_actions()` | `capabilities.yaml` | 动作目录：参数 schema + 前置条件 + 风险等级 |
| `ops_execute(action, params)` | 执行器 ①–⑧ | 成功：观察结果 + 世界变更日志；被拦：`stage` + 规则说明（LLM 可据此自我修正）；需审批：`pending_approval` 票据 |
| `ops_world_state()` | `world.project()` | 当前实体账本快照 |

实现约 60 行：tool handler 里调 `Executor.execute()`，tool description 直接用
本体投影文本。**本体文件零改动**——tool schema 是能力本体的又一种投影（第六种消费者）。

## 5. 理论呼应

无论 Tool 还是 A2A，**协议解决传输，本体解决语义**：
MCP 标准化了「工具怎么暴露」，A2A 标准化了「任务怎么传」，但
「`restart_service` 的前置条件是什么、Incident 何时可关闭」始终来自同一份
`capabilities.yaml` / `core.yaml`。这正是 IETF MACP 草案指出的缺口——
A2A 之上仍需本体层，也是本课程把本体而非协议作为核心的原因。
