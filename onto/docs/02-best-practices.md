# 02 · 本体工程最佳实践与反模式

> 前提：你已读完 [01-理论](01-theory.md)，理解五层本体栈与 TBox/ABox 二分。
> 本文是操作层：怎么把本体真正做出来、养起来、不烂尾。

---

## 一、十条军规

### 军规 1 · 为人写，为机器验证（Dual-Reader Principle）

每个概念都要有**两种表达**：

- **自然语言标注**（`description` 字段）→ 给 LLM 和人类阅读，这是上下文工程的原料；
- **形式化约束**（schema + 规则）→ 给验证器执行，这是护栏的原料。

```yaml
Service:
  description: 可独立部署的运行单元；tier=critical 表示其不可用会直接造成资损   # 给 LLM
  properties:
    tier: {type: enum, values: [critical, standard, experimental]}               # 给验证器
```

只写前者 = 又一份没人看的文档；只写后者 = LLM 理解不好、人类读不懂。
**本体是唯一同时服务这两种读者的资产，这是它相对 prompt 和文档的本质优势。**

### 军规 2 · 从动词开始：能力本体优先

新手直觉是先把领域本体（几百个实体）画完——这是最大的失速陷阱。
正确顺序：

1. 先写**能力本体**：Agent 能做的 5–15 个动作，每个带参数、前置条件、效果、风险；
2. 能力本体里的参数类型会**倒逼**出你真正需要的领域实体（通常只要 5–10 个）；
3. 领域本体按需加粗。

理由：Agent 的价值产生于行动（动词），而非描述（名词）；动词集合小、迭代快、立刻能上护栏。

### 军规 3 · 最小可行本体（MVO），拒绝完备性诱惑

起步预算：**实体类型 ≤ 10，动作 ≤ 15，约束 ≤ 10 条**。
判断标准不是「领域里还有什么没建模」，而是「能力问题（见军规 6）是否都能回答」。
本体的成长方式是**由问题驱动拉取（pull）**，而非由领域驱动推送（push）。

### 军规 4 · 本体即代码（Ontology-as-Code）

把本体当生产代码对待，全套软件工程纪律：

- 进版本库，**代码评审**（本体的 merge 比业务代码更危险——它影响所有 Agent 行为）；
- 语义化版本号：加概念 = minor，改语义/删概念 = major；
- CI 里跑**本体自身的 lint**（schema 自检 + 引用完整性）和**回归测试**（用旧场景回放）；
- breaking change 配**迁移脚本**（实体数据从 v1 形态映射到 v2）。

### 军规 5 · 效果与前置条件必须声明式，不能藏在代码里

动作的业务规则写成**数据**（YAML），而不是散落在 executor 的 if-else 里：

```yaml
restart_service:
  preconditions:
    - exists: {of: Incident, where: {status: open, affected_services: {contains: "$service"}}}
  effects:
    - set: {entity: "$service", field: status, value: healthy}
```

好处：同一份声明既渲染进 LLM 提示词（它知道规矩），又被运行时求值（它拦得住），
还能进文档（人看得懂）。**藏在 Python 里的规则对 LLM 不可见，护栏就变成了盲闸。**

### 军规 6 · 用能力问题（Competency Questions）驱动设计

这是 Stanford 七步法里唯一被现代实践完整保留的步骤，也是防过度工程的解药。
开工前先写下 8–15 个「这个本体必须能回答的问题」：

- 「支付服务超时，最可能的根因依赖是什么？」
- 「重启一个 critical 服务前，哪些条件必须满足？」
- 「当前有哪些未解决的故障，各影响哪些服务？」

每条能力问题映射到至少一条测试：跑一个能回答它的场景。
**删概念的判据：没有任何能力问题需要它。**

### 军规 7 · 风险分级是能力本体的第一公民

每个动作标注 `risk: none/read/low/medium/high`，策略层据此决定审批：

```yaml
rules:
  - when: {risk_in: [high]}
    require: human_approval
```

语义合法性（前置条件）与治理许可（策略）**分开两层**：
前者回答「这个动作在此刻的世界里有没有意义」，后者回答「即使有意义，允不允许做」。
混在同一层会导致改审批流程要动业务语义。

### 军规 8 · 状态变更后必须复验（Post-Condition Validation）

动作效果应用后，**重新验证整个世界状态的约束**；violation 则回滚本次变更并报错：

```
执行动作 → 应用效果(存档快照) → 全量约束验证 → 违反？回滚+报错 : 提交
```

这相当于给 Agent 的每一步装了「事务」。实践中它拦截的是最阴险的一类错误：
单个动作看似合理，组合后把系统带入非法状态（如把 critical 服务缩容到 1 副本）。

### 军规 9 · 给 LLM 的永远是投影，不是全本

上下文是稀缺资源。本体运行时要提供**投影（projection）**能力：
按当前任务相关（相关实体类型 + 参数引用到的实体 + 其一跳邻居）切出切片再渲染。
全本体进 prompt 是 token 浪费和注意力稀释双重罪。

### 军规 10 · 同义词表内建，术语纪律外控

一个概念多个名字（用户/User/客户/customer）是多 Agent 鸡同鸭讲的第一大来源。
在本体里显式维护等价词，投影时归一化到规范名；命名规范（camelCase、单数名词、
动词短语动作）写进 CONTRIBUTING 并在 CI lint。

## 二、六大反模式

| # | 反模式 | 症状 | 解法 |
|---|---|---|---|
| 1 | **本体膨胀**（Ontology Bloat） | 起步就 200 实体 800 关系，三个月没人维护 | 军规 2+3+6：动词优先、MVO、能力问题驱动 |
| 2 | **上帝类**（God Concept） | `Object`/`Thing`/`Data` 下挂一切 | 拆成有明确边界的小概念；问「删掉它谁会痛」 |
| 3 | **过度形式化** | 用 OWL-DL 公理推理闭包，团队无人能改 | 降到 schema+SHACL 级；推理需求真的出现再升档 |
| 4 | **平行宇宙本体** | 每个团队/每个 Agent 私有一份概念定义 | 核心本体（core）+ 领域扩展（extension）分层，见下 |
| 5 | **只写不验** | 本体 красиво 但运行时从不校验，纯装饰 | 军规 8：效果后复验是本体「活着」的证明 |
| 6 | **Prompt 里的影子本体** | 规则真实维护者其实是某个 3k 行 prompt | 军规 5：声明式 + 单一事实源，prompt 只做投影 |

**平行宇宙的解法——核心 + 扩展架构**（OBO Foundry 的教训）：

```
core.yaml        # 跨领域稳定概念：Entity, Relationship, Action, Risk...（变得极慢）
ops-extension    # 运维领域：Service, Incident, Deployment...
biz-extension    # 订单领域：Order, Refund...
```

核心层被所有领域共享，变更门槛最高；领域层各自演化。这是多团队、多 Agent
共享词汇的唯一可持续路径。

## 三、本体工程流程（现代化七步法）

经典 Stanford 七步法的现代精简版，1–2 天可完成第一轮：

1. **定范围**：写能力问题（军规 6），圈定领域边界；
2. **考虑复用**：搜 schema.org / industry ontologies / 公司内部已有本体，能借不造；
3. **枚举核心词**：从能力问题里抽名词（实体候选）和动词（动作候选）；
4. **定类与层级**：is-a 关系只表达真包含（「重启 是 变更动作」✓，「数据库 是 服务」✗——是依赖关系）；
5. **定槽与约束**：属性、类型、枚举、基数、引用完整性；**同时**写 description；
6. **写动作三件套**：参数 + 前置条件 + 效果 + 风险等级（军规 2/5/7）；
7. **创建实例与回测**：造 3–5 个真实场景跑通，能力问题全部可回答才发布 v0.1。

**LLM 的正确用法**（人机分工）：LLM 负责第 3 步抽取候选、第 5 步生成 description 草稿、
对齐同义词；**人负责第 1、4、6 步的语义裁决**——范围和层级错误传播最远，不能外包给概率模型。

## 四、技术选型速查

| 场景 | 推荐 | 理由 |
|---|---|---|
| 团队内部 Agent，快速上手 | **YAML + 自研校验**（本项目路线） | 零依赖、全透明、教学最优 |
| 需要与语义网生态互通 | **LinkML** 或 JSON-LD @context | 有工具链，可生成 OWL/JSON Schema/文档 |
| 企业级、强验证 | **SHACL + RDF**（TopBraid 等引擎） | 约束推理标准化 |
| 学术/重推理 | **OWL 2 (Protégé)** | 表达力天花板 |
| 已有数据平台 | Palantir Ontology / 知识图谱平台 | 全栈但要钱 |

选型判据一句话：**表达力够用就好，治理能力（diff、版本、评审、验证）才是长期瓶颈。**

## 五、健康度自检清单（每季度跑一次）

- [ ] 所有实体/动作都有 description 且不超过 6 个月未更新？
- [ ] 还能背出当前版本的能力问题清单吗？新增了几条？删了几条？
- [ ] 运行时拦截日志里，被前置条件/约束拦下的动作比例是多少？（为 0 = 本体已死，纯装饰）
- [ ] 有没有 Agent 团队绕过本体私加工具定义？（影子本体）
- [ ] 上一次 breaking change 走了迁移脚本吗？
- [ ] 新人能否 30 分钟内读懂 core 并加一个动作？
